# AdOps

[![tests](https://github.com/sergeygubskiy/adops/actions/workflows/tests.yml/badge.svg)](https://github.com/sergeygubskiy/adops/actions/workflows/tests.yml)

> Публичный срез приватного репозитория (разработка с июня 2026); словари, промпты и адаптеры не публикуются.

Настольное приложение для **пакетных операций в рекламных кабинетах Google Ads**:
проверка состояния аккаунтов, пакетное обновление объявлений и перенос расходов
в трекер. Человек вставляет список, движок обрабатывает его пачкой, оператор
подтверждает то, что должно подтверждаться руками.

*Публичная версия — урезанная. Она содержит инженерную обвязку: очередь пакетной
обработки с потолком открытых профилей, Tkinter-интерфейс, клиент REST API трекера,
структуру проверок состояния и тесты на моках. Навигация по самому кабинету не
публикуется. Что осталось за бортом и почему — в конце.*

## Зачем

Рутина в кабинетах упирается не в сложность, а в масштаб: десятки аккаунтов, у
каждого свой профиль браузера, своя скорость загрузки страницы, свой исход.
Наивный скрипт «открой всё, пройдись по всем» ломается тремя способами, и под
каждый из них здесь есть решение:

1. **Машина захлёбывается.** Открыть 40 профилей разом — значит получить тормоза,
   ложные таймауты и падения. Решение — очередь с жёстким потолком: одновременно
   открыто **не больше N** профилей, слот занят от открытия до *подтверждённого*
   закрытия.
2. **«Не вижу проблемы» принимается за «проблемы нет».** На медленном канале
   страница отрисовывается минутами. Решение — вердикт выносится только по
   догруженной странице; не догрузилась — это отдельный статус «не готово», а не «всё хорошо».
3. **Деньги теряются молча.** При переносе расходов в трекер сумма может делиться
   между кампаниями, а округление — съедать копейки. Решение — счёт в целых
   микро-единицах с тестом «сумма долей равна исходной сумме до последней единицы»,
   пробный прогон без записи, бэкап старых значений и честный статус «частично».

## Архитектура

```
     оператор вставляет список имён           оператор вставляет «метка | сумма»
                  |                                          |
                  v                                          v
  +-----------------------------------+      +--------------------------------+
  |  gui/app.py — Tkinter             |      |  (та же вкладка «Расходы»)     |
  |  окно опрашивает очередь событий  |      +--------------------------------+
  |  каждые 100 мс, движка не ждёт    |
  +-----------------------------------+
                  |  события: log | row | open X/N | done
                  v
  +-----------------------------------+
  |  controller.py                    |  каждая операция — свой поток;
  |  потоки + queue.Queue             |  результаты — через очередь
  +-----------------------------------+
        |                       |
        v                       v
  +-------------------+   +-----------------------------------------------+
  |  batch.py         |   |  tracker/sync.py — перенос расходов           |
  |  проверка пачки   |   |   карта «метка -> кампании» (параллельно)     |
  +-------------------+   |   -> план записи (cost.plan_writes)           |
        |                 |   -> dry-run ИЛИ запись + бэкап старых сумм   |
        v                 +-----------------------------------------------+
  +-------------------+            |                    |
  | profiles.py       |            v                    v
  | имя -> id: 0/1/N  |   tracker/cost.py        tracker/api.py
  | (N>1: «неодно-    |   разбор сумм,           клиент REST API:
  | значно», молча    |   раздел по кликам       ретраи, auth отдельно,
  | не открываем)     |   в микро-единицах       ключ маскируется
  +-------------------+
        |
        v
  +-------------------------------------------------------------------+
  |  queue_runner.py — ЯДРО: «не более N открытых профилей»           |
  |                                                                   |
  |   OpenGate          семафор на ЖИЗНЬ открытого профиля. Пермит     |
  |                     берётся ПЕРЕД открытием, отдаётся ПОСЛЕ        |
  |                     подтверждённого закрытия; acquire слышит Стоп  |
  |   ActivePoller      один фоновый источник снимка «что открыто»;    |
  |                     поколения снимков (generation), не время       |
  |   wait_closed       закрытие = отсутствие в ДВУХ РАЗНЫХ опросах    |
  |                     (усечённый ответ API не должен освобождать слот)|
  |   CloseReconciler   окно, оставленное открытым для ручного         |
  |                     разбора, держит слот; вернёт его, когда окно   |
  |                     закроют; предохранитель max_hold               |
  |   run_queue         пул на N слотов; release строго в finally      |
  |                     (release <=> был успешный acquire)             |
  +-------------------------------------------------------------------+
        |
        v
  +-------------------------------------------------------------------+
  |  health.py — структура проверки состояния                         |
  |                                                                   |
  |   1. ждать баланс = доказательство, что страница отрисована       |
  |      (нет — NOT_READY, а не «всё хорошо»)                         |
  |   2. листать карусель уведомлений до конца, копить тексты всех    |
  |   3. второй затвор: нет работающих объявлений + есть отклонённые  |
  |      -> перечитать уведомления                                    |
  |   4. не смогли посчитать — «?», а не ложный ноль                  |
  |                                                                   |
  |   всё, что касается самой страницы, спрятано за протоколом        |
  |   PageProbe (4 метода)                                            |
  +-------------------------------------------------------------------+
        |
        v
  +-------------------------------------------------------------------+
  |  cabinet.py — ИНТЕРФЕЙС-ЗАГЛУШКА                                  |
  |  «навигация по кабинету не публикуется»                           |
  +-------------------------------------------------------------------+
```

Сквозные принципы, которые видны в коде и в тестах:

- **Потолок — инвариант, а не пожелание.** «Открыто <= N» проверяется тестами при
  исключениях в обработчике, при Стопе во время ожидания слота, при двух пачках
  на одном общем потолке и при двойном освобождении (оно не раздувает ёмкость).
- **Каждый отказ называется.** «Не найден», «неоднозначно», «не открылся»,
  «не готово», «частично» — разные исходы, и их нельзя сливать в один.
- **Ключ профиля — идентификатор, а не имя.** Имена не уникальны: имя — это запрос
  с исходами 0 / 1 / N.
- **Пробный прогон и бэкап перед записью.** Запись в трекер адресная, а то, что
  было до неё, сохраняется для отката.

## Стек

Python 3.10+, только стандартная библиотека (`threading`, `queue`, `urllib`,
`tkinter`). Тесты — `pytest`. Зависимостей рантайма нет.

## Как запустить

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt        # только pytest, для тестов
python3 -m adops                       # окно на демо-данных
```

Интерфейс открывается на **синтетических данных** (`adops/demo.py`): фейковый
менеджер профилей и «страницы» с заготовленными состояниями. Видно, как пачка
идёт под потолком, как заполняется таблица по мере готовности и как проблемные
окна держат слоты, пока их не закроют (кнопка «Закрыть открытые»).

Для переноса расходов нужны адрес и ключ трекера. В коде их нет: файл
`~/.adops/tracker.json` (права 600) или переменные окружения.

```bash
export TRACKER_BASE_URL="https://<хост трекера>"
export TRACKER_API_KEY="<ключ>"
```

Пути методов API вынесены в `Endpoints` и переопределяются под конкретный
трекер; значения по умолчанию иллюстративные.

## Масштаб полной версии

Числа ниже относятся к **полному (непубличному) приложению**, а не к этому срезу;
получены из его рабочих логов за ~6 недель эксплуатации:

- **1 773** автоматические проверки состояния аккаунтов в 183 пакетных прогонах;
- пакет из **10+ аккаунтов** при пакетном обновлении объявлений обрабатывается
  примерно за **6 минут** (медиана по 25 пакетам);
- 459 успешных пакетных обработок аккаунтов при 0 ошибок и 3 зависаниях; перед
  каждой правкой делается резервная копия.

## Структура

```
adops/
  queue_runner.py     ядро: OpenGate, ActivePoller, wait_closed, CloseReconciler, run_queue
  batch.py            пакетная проверка: имена -> профили -> очередь -> строки результата
  health.py           структура проверки состояния + протокол PageProbe
  profiles.py         интерфейс менеджера профилей, резолв имён, in-memory реализация
  cabinet.py          интерфейс-заглушка навигации по кабинету
  controller.py       потоки + очередь событий между окном и движком
  demo.py             синтетические данные для запуска без кабинета
  gui/app.py          Tkinter-окно (две вкладки)
  tracker/
    api.py            клиент REST API трекера
    cost.py           разбор ввода, тело запроса, раздел суммы по кликам
    sync.py           оркестрация: карта меток, план, dry-run/запись, бэкап
tests/                pytest, все на моках
```

## Что НЕ входит в публичную версию и почему

Это **урезанная публичная версия**: опубликована инженерная обвязка, а не
механика работы в кабинетах.

- **Навигация по кабинету.** Как найти нужный раздел, что на странице читать и
  куда нажимать — рабочее знание о чужом интерфейсе, которое быстро устаревает и
  не нужно для понимания архитектуры. Вместо него — протокол `PageProbe` и
  заглушка с честным сообщением.
- **Реальный клиент менеджера профилей браузера.** Движку нужны четыре операции
  (`ProfileBackend`); реализация, привязанная к конкретному продукту, не публикуется.
- **Вход в аккаунты и всё, что связано с учётными данными.**
- **Заполнение объявлений и работа с изображениями** — ядро полного продукта.
- **Данные, адреса и ключи.** Рабочие настройки, журналы, идентификаторы
  аккаунтов и параметры подключений в репозиторий не попадают; ключ трекера
  маскируется во всех сообщениях об ошибках, а тест это проверяет.
